## Deviations from the brief and the plan

1. **Reserve kind is `MESSAGE`, not `CHAT`.** The proto has `RESERVE_KIND_MESSAGE` (and the billing contract says `kind = MESSAGE`); there is no `CHAT`.
2. **No `prometheus_client` in the environment.** I wrote a small in-process registry (`app/telemetry/metrics.py`) and a `GET /metrics` text endpoint instead of adding a dependency. Names and labels are as specified.
3. **grpcio and grpcio-tools were already installed and listed in `pyproject.toml`;** I only added them to `requirements.txt`. The stubs are generated by `scripts/gen_billing_proto.py` (`make proto`; Windows: `.venv\Scripts\python scripts\gen_billing_proto.py`) and committed.
4. **IST is a fixed +05:30 offset** (`timezone(timedelta(hours=5, minutes=30))`): `zoneinfo` fails on this Windows install (no `tzdata`), and IST has no daylight saving.
5. **Service-owned limits follow `BILLING_ENFORCEMENT`:** `off` skips them (needed for "exactly like today"), `shadow` decides and logs (`plan_limit_shadow_decision`) but never refuses, `enforce` refuses with 403. Your brief did not say what the limits do in `off`/`shadow`.
6. **Compensation stops at the durable outbox write.** Any failure while persisting (placeholder, counters, outbox batch) releases the hold. Failures after the outbox row exists (cache eviction, soft-deleting the replaced answer) do not, because the request will be answered and billing settles it from the response event.
7. **Counters are written in the request's Postgres session** (`get_db`, committed only if the request succeeds), not in a cross-store transaction (the send itself is a Cassandra batch). A failed send rolls the counter back; the counter write is also guarded atomically (`UPDATE ... WHERE count < limit`), so two sends racing for the last slot cannot both win. A commit failure after a successful Cassandra write would leave the counter one low (lenient).
8. **`defaults_applied.model` is `true` only when a refused saved default became Auto.** In the event the key is added only then (so the `off` payload is unchanged); `MessageResponse.defaults_applied` is always present when the service returns it.
9. **`chat.response.cancelled` is now consumed, but only to record the model** on the existing assistant row (it carries no text). It does not finalize anything and does not set the "request answered" marker, so a late real answer is still accepted.
10. **Request-level dedupe** adds an inbox marker `request.completed` (derived from `request_message_id`) after a successful answer, and also checks the stored row (`status=sent` with content) so it works when the inbox row expired. Pre-existing behaviour kept: an error event followed by a success for the same `response_message_id` is still treated as a duplicate by the old per-response inbox key.
11. **Degraded blocks cap the reading context at 16,000 tokens** (the Free value), as billing cannot say what the plan allows.
12. **Notice naming:** `usage.threshold_reached` becomes `notice_key = usage.threshold_<percent>` with `metric` = billing's `limit` name and `limit` = billing's `allowed`. The frontend copy must key on `notice_key` + `metric`.
13. **Existing tests changed** where the 2.4 bump or new collaborators required it: schema_version assertions (4 tests), `is_completed_reply` and `subscribe(user_id=...)` fakes, and one inbox-save count. No other behaviour was altered.
